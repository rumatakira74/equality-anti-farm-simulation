# Тема A9 — пересчёт анти-фарм-симуляции под фактические параметры платформы — ветка a9-simulation

**Предусловие:** тема A8 (ключи подписи APK) слита в main tnp (merge `c2b4988`). Ветка `a9-simulation` — от свежего `main` репо eq. CI в репо eq не настроен (workflows нет) — правило CI-verify к этой теме не применимо, в отчёте зафиксировать отсутствие CI как факт, номера прогонов не приводить. Живых сетей нет.

**Цель:** выводы раздела 7.7 спеки (доля фермы, безубыточная цена на кошелёк, срок окупаемости) пересчитаны под фактическое состояние платформы: (1) фикс A1 (привязка SPKI листа аттестации к AttestedPublicKey) — «одно устройство ≈ один кошелёк» как стоимостной барьер; (2) фактические PoW-таргеты и параметры Argon2id из кода tnp main; (3) подтверждённый дефект окна челленджа mint. Прогоны воспроизводимы, скрипты воспроизведения в репо.

**Задачи:**

1. **Инвентаризация фактов (шаг 0, tnp — только чтение).** Собрать по коду tnp main (НЕ по докам — они местами устарели): фактические PoW-таргеты (TargetLight/TargetHard) и параметры Argon2id (объём памяти × итерации) из genesis-дефолтов и ядра; механику окна челленджа mint (окно ±48 ч, слот от 1970-эпохи — подтверждён двумя независимыми аудитами дефект: окно открыто для ~6,67 % кошельков в периоде; при K=6 периодов подряд вероятность упустить все окна ~66 % — поглощающее состояние; фикс-вариант A «слот от периода выпуска» требует protocolVersion-bump — решение за владельцем, в этой теме НЕ делать); состояние аттестации после фикса A1 — что даёт повторный кошелёк на устройстве (factory reset / отдельный профиль пользователя Android) в терминах издержек: повторная регистрация, PoW, K покупных поручительств, возраст с нуля, потеря данных/риски. Таблицу собранных фактов с указанием файлов tnp — в отчёт.

2. **Модель устройства/кошелька.** Параметр фермы «кошельков на устройство»: базовый сценарий 1:1 (после A1 — дефолт) + сценарии обхода (2 и 4 кошелька на устройство через factory reset / профили) с явными издержками каждого обхода за кошелёк (время, риск, повторные расходы входа); честная сеть — 1:1. Вопрос для модели: меняет ли экономика фермы существенно, и в какую сторону (доход на кошелёк против издержек обхода).

3. **Стоимость устройства.** В коде модели $120, в README $200 — синхронизировать: взять $200 как публичное значение README, сделать его параметром модели; прогнать чувствительность $120 / $200 / $300. Расхождение и правку — в отчёт.

4. **PoW-таргеты в стоимости кошелька.** Пересчитать стоимость PoW (время × электричество) на кошелёк из фактических таргетов шага 0 — как компонент «стоимости фермы на кошелёк» рядом с устройством, поручительством и комиссией; честно оценить выигрыш GPU/ASIC против среднего телефона при memory-hard параметрах (паритета нет — оценить числом, а не фразой).

5. **Окно челленджа mint в модели.** Доля потерянных выпусков — параметр модели с двумя значениями: (а) «после фикса A» — 0 % потерь (окно достижимо каждый период); (б) «как в коде сейчас» — независимая достижимость ~6,67 % за период с поглощающим состоянием при пропуске K=6 подряд (кошелёк, упустивший окна, теряет выпуск навсегда). Прогнать оба варианта: влияние на честных участников (потерянный доход) и на ферму (её кошельки страдают так же — меняется ли её экономика). Это данные для решения владельца о protocolVersion-bump; сам фикс — вне темы.

6. **Прогоны.** Базовые сценарии раздела 7.7 (K = 3, слоты 3/5/10, посев 100, ферма 20 устр./мес., 8 прогонов × 60 мес., фиксированные seed) + вариации по пунктам 2–5. Новые параметры — отдельными режимами/флагами, RNG и поведение базовой модели не менять (канарейка регрессии 1.1 обязательна, до и после). CSV в Mistral/results по конвенции репо. Тесты: python3 test_farm_model.py зелёные + новые тесты на добавленную механику (кошельки/устройство, окно mint, стоимость PoW).

7. **Скрипты воспроизведения и отчёт.** Патч/режим воспроизведения всех новых прогонов — в репо (одной командой с seed), чтобы любой прогон повторялся байт-в-байт. Отчёт `reports/REPORT-A9-SIMULATION.md`: сравнение старых выводов 7.7 с новыми (доля фермы, безубыточная цена, срок окупаемости) — таблица «параметр → старое → новое → влияние»; предложения по обновлению раздела 7.7 спеки (после merge; спеку НЕ править); изменённые файлы; факт отсутствия CI в eq. Большие артефакты (>1 МБ: сводные CSV, логи прогонов) — R2 `tnp-artifacts` (`wrangler r2 object put`), в репо — только SHA-256 + путь; предохранитель: wrangler не авторизован → записать диагностику в отчёт и продолжить без R2 (тема не падает из-за облака). Секреты, ключи, токены в R2 не класть.

**Предкоммитная проверка (обязательно):** python3 test_farm_model.py — зелёный (с новыми тестами); канарейка регрессии базовой модели 1.1 — пройдена до и после изменений; `git status` чист; файлов больше 1 МБ в коммитах нет.

**Финализация:**

- Промежуточные коммиты раз в ~30 минут (номер сессии в сообщениях коммитов); после рестарта сессии — до любых действий сверить живое состояние с последним коммитом ветки и отчитаться планом.
- Ресурсная дисциплина: тяжёлые параллельные прогоны не запускать; прогоны симуляции — по одному за раз.
- Финальный коммит — чистое дерево; ветку `a9-simulation` запушить.
- Merge в `main` НЕ делать: только после слепого аудита ветки (по отдельному промпту после пуша) и подтверждения владельца.

**Правила:** предмет темы — только пересчёт симуляции в репо eq. НЕ трогать: код tnp (включая дефект окна mint и его фикс), спеку tnp, genesis, protocolVersion, README tnp (тема A10), RNG и поведение базовой модели вне добавляемых режимов (канарейка 1.1), ветки вне a9-simulation. Не коммитить файлы больше 1 МБ; сумма артефактов темы — до ~5 МБ. Находка вне мандата — FINDING-*.txt + коммит с пометкой + продолжать; критический блокер прогона — с пометкой «критический блокер прогона». Если для продолжения нужно действие, доступное только владельцу, ИЛИ ты заблокирован и есть риск ошибки, напрасной работы или перерасхода токенов (включая выбор между равнозначными механиками) — остановись и задай один конкретный стоп-вопрос в чате; лучше один короткий вопрос, чем цикл попыток; продолжать после ответа.
